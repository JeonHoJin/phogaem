# 보안 점검과 검증

2026-11-05 점검. 합성 데이터와 독립 로컬 PostgreSQL·core·gateway·sidecar로 검증했다. 보안 검증은 운영 데이터·계정과 R2를 변경하지 않았다. 후속 배포에서 Mac의 Phogaem 사이드카를 갱신했고, 프런트엔드 변경은 이 커밋의 Pages 배포 워크플로를 통해 반영된다. 코어·Postgres·다른 사이드카는 재시작하지 않았다.

## 수정한 사항

- 인증 증명과 사진 본문이 HTTP 리다이렉트 대상으로 전달되지 않도록 모든 클라이언트 요청에 `redirect: error`를 적용한다. 쿠키·referrer를 보내지 않고 HTTP 캐시를 사용하지 않는다. API origin과 요청 경로를 인증 전에 검증한다.
- 계정 연결·세션 초기화 후 늦게 도착한 이전 로그인이나 API 응답은 폐기한다. 이전 기기 키 생성이 새 패스키 계정의 키를 덮어쓰지 않도록 순서를 보장한다.
- 배치 업로드 중 승인 취소는 오류 종류를 보존하여 보호된 화면을 비운다. 이미 처리된 파일 수를 표시하고 불필요한 재조회는 하지 않는다.
- 초기 로컬 저장소 조회가 끝나기 전 공유 연결을 차단하고, 보관함 종류가 바뀐 뒤 오래된 로딩 결과가 새 화면을 덮어쓰지 않도록 한다.
- 로컬 업로드에서 위험한 MIME·확장자 위장을 거부한다. 백엔드는 확장자·MIME·실제 포맷 헤더를 함께 검사한다. 서버는 JSON 1MiB와 사진 16MiB 한도를 구분하고 메타데이터·초대·원본·거부 응답에 `private, no-store`와 `nosniff`를 설정한다. 빈 core token 설정은 접근을 거부한다.
- 실제 배포 HTML에 CSP와 `no-referrer`를 적용한다. 스크립트·스타일은 같은 origin, 사진은 같은 origin/Blob/data, 연결은 같은 origin과 설정된 API만 허용한다. 인라인 스크립트·객체·프레임·폼 전송·base URL 변경을 차단한다. 개발 HMR에는 이 CSP를 적용하지 않는다.

## 반복 검증

```sh
npm run lint
npm test
npm run test:vision
npm run build
npm run test:e2e
npm run test:production
npm run test:shared
npm audit --audit-level=high
```

Node 30개, Python 도구 10개, 로컬 브라우저 14개, 배포 빌드 브라우저 2개, 실제 공유 스택 브라우저 5개를 검사한다. 공유 테스트는 빈 웹 포트를 사용하므로 기존 5174 개발 서버를 중지할 필요가 없다. 별도 mlhops 사이드카 테스트는 독립 DB에서 단위 5개·HTTP/DB 10개를 실행하고 clippy와 fmt도 검사한다.

공유 통합 검증에는 클라이언트 필터를 우회한 원시 위조 헤더, 변조 JWT, 다른 보관함의 읽기·쓰기, 승인 취소, 패스키 계정 연결을 포함한다. 백엔드 검증에는 초대 만료·교체, 동시 요청 한도, 원본 유실·변조, 다른 앨범의 사진 ID가 섞인 기록 갱신의 전체 거부를 포함한다. 실제 307 서버와 배포 CSP 브라우저 테스트로 네트워크 차단도 검증한다.

Pages CI는 의존성 high/critical 감사 및 배포 산출물 테스트를 통과해야 배포한다. 공유 스택·Rust 테스트는 현재 인접 mlhops 작업본이 필요하므로 Pages CI에는 포함하지 않는다. 백엔드 변경 시 위 로컬 통합 검증이 별도로 필요하다. 새 후처리·R2 계층은 [후처리](processing.md)의 프로세스 수명·권한·용량 예약 검증도 수행한다.

## 남는 경계

- `jeonhojin.github.io`의 다른 앱과 origin 및 패스키 RP를 공유한다. 경로별 IndexedDB 이름은 이름 충돌 방지이며 접근 통제가 아니다. 같은 origin의 다른 앱이 침해되면 Phogaem 저장소에도 영향을 줄 수 있다. 앱 단위 격리가 필요하면 별도 origin과 인증 정책을 함께 설계해야 한다.
- GitHub Pages HTML meta CSP로는 `frame-ancestors`를 설정할 수 없다. 따라서 이번 변경은 외부 사이트가 이 페이지를 iframe으로 삽입하는 것까지 막았다고 보장하지 않는다. 이를 강제하려면 응답 헤더를 제어할 수 있는 호스팅 구성이 필요하다. [CSP 명세](https://www.w3.org/TR/CSP3/#meta-element)
- 파일 시그니처 검증은 전체 이미지 디코딩·악성코드 검사·압축 해제 후 픽셀 수 제한이 아니다. 변환/썸네일 도입 시 별도 격리와 디코딩 자원 한도가 필요하다.
- 이미 다운로드되거나 브라우저 메모리에 전달된 사진을 승인 취소로 회수할 수는 없다. 취소는 다음 서버 요청부터 적용하고, 앱이 취소 응답을 받으면 공유 화면을 비운다.
- 삭제·자동 만료·고아 원본 정리는 아직 없다. 보관함별 한도는 서버 디스크 전체 용량의 상한이 아니다. 사용 범위 확대 전 전체 용량 관리와 백업·복구 검증이 필요하다.

이 검증은 발견한 결함과 회귀 위험을 줄이는 작업이며, 모든 공격 가능성이 없다는 보장은 아니다.
