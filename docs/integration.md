# mlhops 공유보관함 통합

## 구현된 흐름

브라우저는 기존 mlhops 기기 키·패스키로 로그인하고, 게이트웨이의 `phogaem-*` op를 통해 공유보관함에 접근한다. 8개 op 모두 관리자 승인이 필요하며, 코어의 계정 승인과 사이드카의 보관함 멤버십을 함께 검사한다. 화면을 열기만 해서는 로그인·계정 생성·서버 호출을 하지 않는다. [계정 승인과 패스키 공유 안내](approval.md)를 참고한다.

프런트엔드는 이 레포의 `apps/web/src/server/`, 백엔드는 별도 mlhops 레포의 `sidecars/phogaem/`에 있다. 코어·게이트웨이 코드는 수정하지 않았다. 버전이 있는 8개 op와 서버 설정의 정확한 계약은 mlhops 사이드카 README를 따른다.

- 공유보관함 생성·선택·새로고침.
- 소유자가 만든 24시간 초대 링크로 참여. 링크를 새로 만들면 이전 링크는 무효가 된다.
- 서버가 원본을 SHA-256으로 검증하고 같은 보관함의 완전 동일 파일을 통합. 업로더는 각각 보존.
- 멤버만 메타데이터·원본·자신의 다운로드 기록을 조회·수정.
- 기기 키는 앱 경로별 IndexedDB에 보관하고 토큰은 메모리에서만 사용.
- 패스키 등록·기존 계정 로그인·새 기기 키 연결.

## 격리된 로컬 통합 테스트

필요 조건: 이 레포와 나란히 있는 `../mlhops`, Rust/Cargo, `initdb`·`pg_ctl`이 PATH에 있는 PostgreSQL, Node.js·npm, Chrome 또는 Playwright Chromium.

```sh
npm ci
npm run test:shared
```

스크립트가 전용 임시 PostgreSQL 클러스터와 코어·게이트웨이·사이드카를 모두 loopback의 빈 포트에 띄운 뒤, 실제 브라우저 계정으로 테스트한다. 인증 서버나 사이드카를 모킹하지 않는다. 종료 시 직접 시작한 서비스만 정지한다.

운영 DB·비밀 파일·등록 토큰을 읽지 않는다. 테스트용 DB URL·키·원본·로그는 Git에서 제외된 `.local/dev-mlhops/run-*/`에만 생성한다. 기존 운영 서버나 Postgres 서비스를 재시작하지 않는다. TLS 인증서 발급·Cloudflare 요청·배포도 수행하지 않는다.

## 직접 화면 보기

첫 터미널:

```sh
npm run dev:server
```

출력된 로컬 게이트웨이 주소를 두 번째 터미널의 환경변수에 넣는다. `<printed-port>`는 실제 출력값으로 바꾼다.

```sh
VITE_MLHOPS_API_BASE=http://127.0.0.1:<printed-port> npm run dev -- --port 5174
```

http://localhost:5174/phogaem/ 에서 ‘공유보관함 연결’ → ‘이 기기로 연결’ → 보관함 생성 또는 초대 참여를 진행한다. 패스키의 로컬 RP는 `localhost`이므로 직접 보기에서도 `127.0.0.1` 대신 `localhost` 페이지를 사용한다. HTTP 게이트웨이 자체는 loopback에만 열린다.

이 스택은 개발용이다. 실행마다 새 데이터베이스를 만들며 이전 실행의 원본·DB 파일은 진단을 위해 남긴다. 같은 실행 중 다른 브라우저 프로필로 초대 링크를 열면 다른 사용자로 공유를 시험할 수 있다. 별도로 배포된 운영 사이트와 데이터·계정은 공유하지 않는다.

## 원본과 요청 한도

공유 모드 원본은 서버의 로컬 디렉터리, 메타데이터는 Postgres에 저장한다. 파일 본문은 JSON/base64로 바꾸지 않고 게이트웨이를 통해 그대로 전달한다. 현재 게이트웨이가 업로드를 메모리에 모으므로 공유 모드 파일당 최대 16MiB로 제한한다. 브라우저만 사용하는 기기 보관함은 기존 50MiB 한도를 유지한다.

보관함당 원본 최대 2GiB·2,000장·멤버 16명, 사용자당 생성 보관함 32개다. 삭제·자동 만료는 현재 제공하지 않는다. 초대 유효기간과 사진 보관기간은 별개다.

원본 미리보기는 화면 근처에서 지연 로드하고 화면 밖에서는 Blob URL을 해제한다. 파일 조회는 350ms 간격·최대 2개 응답 처리로 제한하며, 429는 GET에 한해 한 번 재시도한다. 메타데이터나 다운로드 기록 갱신만으로 같은 원본을 다시 불러오지 않는다. 썸네일 변환은 아직 없으므로 원본이 큰 경우 미리보기에도 해당 크기의 전송이 필요하다.

서버 업로드는 파일별로 확정한다. 프런트엔드는 최대 2개를 병렬 전송하고 업로드/원본 조회의 시작을 공통 250ms, 각 종류는 최소 350ms 간격으로 제한한다. 메타데이터·인증 요청과 다른 기기의 트래픽은 별도이므로 이 제한이 IP 전체의 429를 완전히 방지한다고 보장하지 않는다. 자동 업로드 재시도는 하지 않는다. 각 완료 응답의 사진을 즉시 목록에 합치고 마지막에 목록을 한 번 재조회한다. 완료 순서와 파일 선택 순서는 독립적이며 성공한 파일을 재시도 목록에서 제거한다. 실패 시 새 전송을 중단하고 이미 시작한 요청을 정리한다. 승인 거부를 받으면 정리를 기다리지 않고 보호된 화면을 비운다. 여러 파일 중간에 실패하면 먼저 성공한 파일은 남으며 화면을 갱신해 결과를 표시한다. ‘받았음’은 사용자의 수령 확인 기록으로, 원본 조회·미리보기와 구분한다. DB 커밋 실패 시 참조되지 않는 원본 파일이 남을 수 있으며 후속 정리 기능에서 처리한다.

## 후속 단계

운영 백엔드와 GitHub Pages 배포를 완료했다. 전용 DB 역할·스키마와 원본 디렉터리를 사용하고, Phogaem만 시스템 자동 실행 서비스로 등록했다. 기존 코어·Postgres·OCR·roster 프로세스는 재시작하지 않았다. R2 전환은 후속 단계다. 공개 사이트와 배포 절차는 [Pages 안내](pages.md)를 따른다.

### 운영 배포 검증

공개 게이트웨이에서 `phogaem-*` 8개 op가 등록되어 있으며 모두 `auth: approved`인 것을 운영 관리 API에서 확인했다. 각 op의 미로그인 요청은 `401 sign-in required`, 사이드카 직접 접근은 `403`이다. 운영용 DB 마이그레이션과 파일 권한, 자동 실행 서비스의 실행 상태를 확인했다.

실제 승인 계정의 운영 업로드·다운로드 왕복은 Pages 배포 후 브라우저에서 최종 확인한다. 운영 테스트를 위해 새 계정을 자동 승인하거나 기존 사용자 데이터를 변경하지 않았다. 원본은 운영 서버 로컬에 저장하며 R2는 연결하지 않았다.
